# Development Sandbox

The repository doubles as its own dev environment: the root `astro.config.mjs` is a working EmDash site that registers the plugin directly from source, backed by a local SQLite database (`sandbox.db`, present in the working tree but git-ignored from the published package). This is the fastest way to exercise the plugin in a real admin and a real render path without publishing.

## Scripts

Two npm scripts drive the sandbox (`package.json#L8-L9`):

- `npm run sandbox:init` → `emdash init -d ./sandbox.db --force` — (re)creates and seeds the sandbox database.
- `npm run sandbox:dev` → `astro dev` — runs the dev server.

## The sandbox site (`astro.config.mjs`)

`astro.config.mjs#L8-L33` configures:

- `site: http://localhost:4323`, `server.port: 4323` — the fixed local port (the sandbox plan notes ports must not drift between plugins);
- `output: "server"` with `@astrojs/node` in `standalone` mode — the Node adapter supports the CMS's session cookies/credentials, mirroring how a real deployment runs;
- `@astrojs/react()` — the admin UI needs React;
- `vite.server.fs.allow: [".."]` — lets Vite serve the parent directory during local development;
- the `emdash` integration with `database: sqlite({ url: "file:./sandbox.db" })` and `plugins: [codeBlockProPlugin()]` — the plugin imported straight from `./src/index.ts`, so edits to the descriptor or block fields are picked up immediately.

## Content collections (`src/live.config.ts`)

`src/live.config.ts` declares the live collection EmDash's runtime reads:

```ts
export const collections = {
  _emdash: defineLiveCollection({ loader: emdashLoader() }),
};
```

`defineLiveCollection` comes from `astro:content` and `emdashLoader` from `emdash/runtime`; the `_emdash` collection is the bridge that lets site pages query CMS content at request time in the server output mode. `src/__tests__/dependency.test.ts` smoke-checks that `emdash/runtime` resolves and exports `emdashLoader` and `getDb`.

## Generated types (`emdash-env.d.ts`)

`emdash-env.d.ts` is generated by EmDash on dev server start and marked "Do not edit manually". It references `emdash/locals` and augments the `emdash` module with `Page` and `Post` collection interfaces — id, slug, status, title, `content?: PortableTextBlock[]`, timestamps, and optional bylines (plus a `featured_image` on `Post`). These are sandbox-scoped types for the demo content model, not part of the plugin's published contract.

The `files` array in `package.json` (`src`, `docs`, `README.md`, `LICENSE`) is the allowlist for the npm package, so all of this sandbox machinery — `astro.config.mjs`, `sandbox.db`, `src/live.config.ts`, the generated env types — stays out of the published artifact (see [Packaging, Publishing, and CI](/openwiki/operations/packaging-and-release.md)). Unit tests don't need the sandbox at all: they run the real Astro component in a Vitest container with a mocked `virtual:emdash` module ([Test Suites and Harness](/openwiki/testing.md)).

## Historical direction

`docs/sandbox-plan.md` is a proposal to move exactly this boilerplate out of plugin repos and into an `emdash sandbox` CLI (or a monorepo scaffolding script) that generates the Astro config, live collection, and preview routes on the fly. It documents the *intent* behind the current layout — one-command local testing without per-repo drift — but none of it is implemented here; the local boilerplate remains the working mechanism.
